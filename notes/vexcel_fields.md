# Vexcel precomputed fields

Generated by `python scripts/vexcel_test.py` for three Houston CoStar apartment properties (`propertyType == 11`, `primaryAddress.researchMarketId == 14`), selected by ascending property id with coordinates.
The local quickstart and 13-page tutorial were read for request conventions and field meanings; neither reference file is copied into the repository.

## Requests and saved artifacts

GET `property/extract`: longitude-first `POINT(lon lat)`, SRID 4326, latest=true, include=precomputed, unit-system=imperial, layers urban/urban-r/wide-area/urban-g.
POST `ortho/extract`: an approximately 80 m square constructed with shapely.box using the quickstart's local metres-to-degrees approximation, plus its 10 m context buffer, bounding_box crop, JPEG, and gold outline.
Responses are cached under git-ignored `data/cache/vexcel/`. USE_CACHE_ONLY prohibits network calls. Requests use only the X-API-KEY header for authentication, with up to five exponential-backoff retries on 429.

## Complete field inventory

Paths use bracket notation so dots inside Vexcel attribute names are literal. `[*]` preserves feature/structure order as nested arrays in each value. All leaf fields (including empty containers), metadata and geometry values are included without truncation.
JSON null means reported null; `<not returned>` means the key was absent or that no successful precomputed response was available. Zero and false remain reported values. Meanings explicitly marked 'interpretation from key' are inferred; the tutorial does not document every field or category scale.
Parcel-level attributes cover the Vexcel parcel, which need not match a CoStar community boundary. The 80 m imagery square may cover only part of a large community. A tree-cover percentage is not total green cover, and a detected vehicle count cannot validate parking-space capacity.
